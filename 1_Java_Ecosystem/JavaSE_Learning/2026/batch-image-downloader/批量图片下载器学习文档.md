## 📐 项目需求描述

### 业务场景
> 假设你是一个电商平台的后台开发工程师。
> 运营同学给了你一份包含 **100 个商品图片 URL** 的列表。
> 你需要把这些图片全部下载到本地，用于离线备份或审核。

### 功能要求
- ✅ 读取 URL 列表（可以写死在代码里，模拟即可）
- ✅ 并发下载，**同时最多 10 个线程在工作**
- ✅ 每张图片下载成功后，打印进度（第几张 / 共多少张）
- ✅ 所有图片下载完成后，打印总耗时
- ✅ 某张图片下载失败时，打印错误信息，但**不能影响其他图片的下载**

## 🏗️ 代码结构设计

```
src/
└── main/
    └── java/
        └── com/practice/downloader/
            ├── ImageDownloader.java       ← 主类，程序入口
            ├── DownloadTask.java          ← 单个下载任务（实现 Callable）
            ├── ThreadPoolConfig.java      ← 线程池的配置与创建
            └── ProgressTracker.java       ← 进度统计（线程安全）
```

### 各个类的职责说明

#### `ImageDownloader.java` — 主入口
- 持有 URL 列表
- 创建线程池
- 把每个 URL 封装成 `DownloadTask` 提交给线程池
- 等待所有任务完成，打印总耗时

#### `DownloadTask.java` — 下载任务
- 实现 `Callable<Boolean>`（返回下载是否成功）
- 内部负责真正的 HTTP 请求和文件写入
- **自己处理异常**，不向上抛出

#### `ThreadPoolConfig.java` — 线程池工厂
- 统一管理线程池的创建
- 在这里你会亲手写 `new ThreadPoolExecutor(...)` 的 7 个参数
- 遵循阿里巴巴规范：**禁止用 `Executors.newFixedThreadPool()`**

#### `ProgressTracker.java` — 进度追踪
- 用 `AtomicInteger` 统计已完成数量（线程安全）
- 打印 "已下载 3/100" 这样的进度信息

## 🚧 我们会故意踩的坑（最有价值的部分）

> 光写出能跑的代码不够，你还需要理解"错了会怎样"。

### 坑 1：用 `Executors.newFixedThreadPool()` 会发生什么？
- 它内部用的是**无界队列** `LinkedBlockingQueue`
- 100 万个任务全堆进去，内存溢出（OOM）
- 这就是为什么阿里规范明确禁止它

### 坑 2：线程池队列设太小会发生什么？
- 任务提交速度 > 消费速度时，队列满
- 触发**拒绝策略**，任务被丢弃或抛出异常
- 你会亲眼看到 `RejectedExecutionException`

### 坑 3：`future.get()` 不加超时会发生什么？
- 如果某个 URL 无响应，这行代码会**永远卡住**
- 正确写法：`future.get(5, TimeUnit.SECONDS)`

### 坑 4：在任务内部不 catch 异常会发生什么？
- 一个 URL 下载失败，整个批次任务全部停止
- 正确做法：每个任务内部独立处理自己的异常
