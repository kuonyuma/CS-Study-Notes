# 1. 协议格式

我们先来看看TCP的协议格式。
![、](https://i-blog.csdnimg.cn/direct/9ba39d68ffaa439881ec535452db383d.png)
源端口号与目的端口号很好理解，就是数据应该从哪一个进程出发到哪一个进程中。
32位序号与32位确认序号，这里暂时不讲。
4位首部长度表示的是TCP头部的长度，4位的最大二进制是1111转化为十进制是15，由于这里的单位是4字节，所以TCP头部总长度最大也就是15 * 4为60字节。
保留6位的意思是如果以后四位首部长度不够用了，那么就从这里再拿一点，保证了扩展性。
我们暂且了解到这里即可。

# 2. 确认应答

我们知道TCP具有连接可靠性，那它是如何保证可靠性的呢？
其实就是这里的确认应答。

我们看看一个生活中的场景。

（我正在通过wx给小美发送消息）
我：小美小美，星期六我们去吃火锅吧。
我：小美小美，做我女朋友吧。
小美：好的好的。
小美：滚~

这里，我通过小美的回信知道了小美收到了我的信息，知道了星期六她会出来，这样就好规划星期六的行程。
同时也知道了她不同意做我女朋友，悲~
但问题来了，网络环境是很复杂的，可能会出现后发先至的情况。

比如
（我正在通过wx给小美发送消息）
我：小美小美，星期六我们去吃火锅吧。
我：小美小美，做我女朋友吧。
小美：滚~
小美：好的好的。

这里，小美的原意肯定是同意和我去吃饭，但是不同意做我女朋友，
但是由于“滚~”这一条信息比“好的好的”先发出去，从而造成了我理解上的混乱。
此时我就会想： 做我女朋友？但是不和我出去吃饭？？这是PLAY的一环吗？？


再比如：
结过婚的都知道，婚车一开始在新郎这里按照一定顺序排好了的：尾车->车7->车6->车5->车4->车3->车2->头车。
大家整整齐齐的出发，开往新娘那边。
实际上，大家一出村，或许就走散了~。
大街上的红绿灯、其他车辆，都会造成婚车走散的情况。
走散后肯定只能一路往前开了呗，中途不会再次集结的。
这样可能就会出现，尾车比新郎乘坐的头车先到新娘家里。
那新娘会坐上尾车吗？...这显然是不合适的吧...
那尾车就只能等大家都到了，新郎到了，新娘上车，车队重新排好，开向酒店。

那如何应对这种情况呢？做法就是给汉字标号。

我：小美小美，星期六我们去吃火锅吧（1）。
我：小美小美，做我女朋友吧（2）。
小美：好的好的（针对1）。
小美：滚~（针对2）。

这样即使顺序乱了，我也知道小美不想做我女朋友。



TCP的处理方式也是一样的，由于TCP是以字节流的形式进行传输的，所以我们给每一个字节标号。
此时A与B正在进行TCP通信，发送了两条信息。


![在这里插入图片描述](https://i-blog.csdnimg.cn/direct/3fcab74e89c1467c893ba0a50b264cf2.png)

第一步：
主机A给主机B发送数据（1-1000）。

第二步：
这里我们就要讲到TCP中的六位标志位中的ACK位。
![在这里插入图片描述](https://i-blog.csdnimg.cn/direct/645d386d66ca46a8ad98be76856fb693.png)
此时B接收到信息并返回，将ACK位中的0换为1，代表这不仅是个普通包，它里面包含了来自B的确认信息。
这里的确认信息就是32位确认序号，此时确认序号为1001（载荷数据最后一位+1）。

A读取了B的数据报头，看到ACK为1，知道了确认序号中有信息从而去读取，发现序号为1001，就知道B已经收到了A发的1-1000的数据。
此时A发送1001-2000的数据。
此时B收到数据，将ACK转化为1，确认序号为2001，返回A，A知道B收到信息。

这种方式有效地保证了传输的可靠性。
也避免了由于后发先至引发的问题。

此时假设1001-2000先到达了B端，此时B接收，但B还未接收到1-1000这条数据，1001-2000这条数据就会在B的接收缓冲区中暂时存储。等收到1-1000后再按顺序接收数据。
假设1-1000数据在网络中丢失了，B也会返回确认序号1，A得到确认序号1知道1-1000这条数据送丢了也会重新发送。

# 3. 超时重传
我们想想标号这样的操作可以应对数据丢失的问题吗？
毕竟网络上数据丢失是很正常的事情了。
在TCP中数据丢失有两种情况：
1. A发送给B的数据丢失了
2. B返回给A的ACK丢失了。

其实TCP里面有一个计时的功能，
如果迟迟未收到来自B的ACK，不管是第一种情况还是第二种情况，A都会重新发送数据。
比如：A发送1-1000的数据给B，
不论是第一种情况还是第二种情况，
其实都可以归结为A未收到ACK，此时超过一定时间后，A就会重发1-1000这段数据。
这就是超时重传。
这个时间不是一个具体数字，会根据外在环境动态的变化。
所以TCP是可以应对数据丢失问题的，TCP的传输可靠性很大程度上，依靠的就是超时重传与确认应答，网上所说的三次握手也只是在开头建立连接那一段时间有用，
后续的业务数据交互与三次握手也没太大的关系了，再说三次握手，能够握上手也是依靠确认应答和超时重传的。
# 4. 连接管理
当两台机器利用TCP协议进行通信的时候，双方会建立一个逻辑上的连接关系。即互相储存对方的信息（IP与端口）。
要知道如何建立关系我们就得学习三次握手。
要知道如何删除关系我们就得学习四次挥手。

## 三次握手
首先还是先来看一张图片：

![三次握手简图](https://i-blog.csdnimg.cn/direct/ddcd855e0bad4a289d81095280d22af6.png)

这里左边代表客户端，右边代表服务器。

SYN是TCP六位标志位中的一位，当两台机器之间初次握手的时候SYN会被置为1。
SYN也是synchronize，这个单词我们在多线程中也见过，在那里代表的是锁，这里代表的是同步（对于TCP而言主要指同步双方的初始序号）。

1. 第一次握手
首先客户端给服务器发送建立关系的请求。
此时客户端的报头中的SYN置为1，且不携带业务数据（即不包含有效载荷）。
客户端的状态变为SYN_SENT。

2. 第二次握手
服务器接收到来自客户端的请求，获得客户端的IP和端口，此时状态变成SYN_RCVD。
同时返回一个ACK和SYN。
ACK与SYN其实是同时发送给客户端的，它们在同一个TCP报文首部中。

3. 第三次握手
客户端收到来自服务器的ACK，知道了服务器存储了客户端的信息；
收到SYN，客户端存储服务器的信息。
服务器的ACK与SYN如果被确认无误，客户端状态变为ESTABLISHED。
客户端返回一个ACK告诉服务器，客户端已存储服务器的信息。
服务器收到ACK后，状态变为ESTABLISHED。

到此，三次握手完毕，客户端与服务器建立连接关系。

问题--如果当客户端返回的ACK丢失后怎么办？

1. 情况一 
正常传输纠正：
由于客户端的状态变成了ESTABLISHED，表示客户端认为连接已经建立了，后续的报文中ACK都是1。
站在客户端的角度连接已经建立了，那么客户端发送业务数据时，服务器看到ACK为1，而且确认序号正确，此时服务器的状态也会变为ESTABLISHED。
这样就被纠正过来了。
2. 情况二
超时重传：
来自客户端的ACK丢失了，站在服务器的角度，它还可能认为是自己发送的SYN+ACK丢失了。此时服务器会重新发送SYN+ACK，客户端收到重复的SYN+ACK，知道了自己上一次发送的ACK丢失了，就会重新发送ACK。这样连接也有机会重新建立。

3. 情况三
连接断开：
服务器重新发送SYN+ACK后迟迟得不到来自客户端的ACK，一定时间后连接断开，服务器删除客户端的IP与端口。


## 四次挥手
首先看看这张图片
![在这里插入图片描述](https://i-blog.csdnimg.cn/direct/3aa71d76294248f483956b54caaca16b.png)
这里的FIN也就是六位标志位中的一位。

1. 第一次挥手
首先客户端发起FIN，表示客户端不会再往服务器发送数据了。
此时状态变为FIN_WAIT_1。这个状态代表的是我不会传数据，但我还能接受数据。客户端->服务器这个通道处于半关闭。

2. 第二次挥手
服务器收到FIN，并返回ACK，表示知道了客户端不会传递数据过来了。
此时服务器状态变为CLOSE_WAIT。客户端收到此ACK后，状态改为FIN_WAIT_2。
FIN_WAIT_2代表的含义是，客户端收到了服务器对FIN的确认，此时客户端在单向等待服务器发送它的FIN包。
在此期间，服务器还可能有数据没发送完，可以继续向客户端发送。

3. 第三次挥手
等待一段时间后，如果服务器也没有数据要发送了，服务器就会发送FIN，表示服务器已经没有数据要给客户端了，服务器->客户端这个通道也将要关闭。


4. 第四次挥手
客户端收到FIN，返回ACK，状态变为TIME_WAIT。
服务器收到客户端的ACK，状态改变为CLOSED，删除客户端的信息。
等待 2MSL（最大报文段生存时间）后，客户端状态也会变为CLOSED，此时删除服务器的信息。

关于客户端的TIME_WAIT状态。
之所以客户端收到来自服务器的FIN后，没有立即进入CLOSED状态，是因为ACK存在丢失的可能性。
假设客户端发送的ACK由于某种原因导致服务器未收到，此时一段时间后（对！这里也有超时重传）服务器会重复发送FIN，诱导客户端重新发送ACK。有了 TIME_WAIT 状态及其持续的时间保证了，服务器能够收到最后的 ACK 从而正常关闭连接。




# 总结

1. TCP协议通过报头中的首部字段进行控制，确保数据在不同进程间的准确传递。
2. 确认应答机制利用序列号和确认序号解决了数据包后发先至的问题，保证传输的可靠性。
3. 超时重传机制有效应对了网络中数据或ACK丢失的情况，是保障可靠性的重要手段。
4. 连接管理通过三次握手建立可靠的逻辑连接，并通过四次挥手安全断开连接。
