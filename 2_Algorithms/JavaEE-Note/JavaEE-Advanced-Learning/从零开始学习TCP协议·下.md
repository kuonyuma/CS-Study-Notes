# 1. 延迟应答
上次我们谈到拥塞控制和流量控制。它们的目的都是为了限制滑动窗口的大小，也是增加效率的同时也要保证可靠性的一种手段。
这里我们聊到的延迟应答也是提高效率的一种手段。

客户端给服务器主动发起通信的时候，服务器返回的ACK中，会含有一个叫做窗口大小的信息。这个信息决定了客户端还能给服务器批量发送多少条数据。
我们尽可能地让这个窗口扩大，从而引入延迟应答这个概念。

信息都是先发送到一个接收缓冲区中的，服务器从这个缓冲区中获取数据，客户端从这个缓冲区灌注数据。在相同时间下如果服务器获取数据的速度比客户端输入信息速度快的话。那么缓冲区的余量就会扩大，滑动窗口也就会扩大。

延迟应答就是，当客户端发送数据过来时，服务器不会立刻返回ACK，而是等一会才会返回ACK。这里等一会的目的就是为了消耗更多的数据，使得返回ACK时，缓冲区的余量足够大。使得下次客户端批量传递的数据更多。

也有人会疑问。这里多等一下，会不会降低传递数据的速度。
这里有一个思想叫做，牺牲微观速度换取宏观的速度。

假设：
	此时服务器的缓冲区总共有10kb大小，现在里面残留了9kb的数据未读取完，
	现在收到了来自客户端的1kb数据。此时缓冲区满了。如果立刻回复ACK，那么客户端就不会再传递新的数据过来。如果等一下，服务器把缓冲区里面的10kb数据一次性读走了，在返回的ACK报文中，宣告的“窗口大小”就变大了（比如变成10kb），此时客户端就知道自己可以批量发送10kb的数据过来。

![在这里插入图片描述](https://i-blog.csdnimg.cn/direct/72299621672048fd946e9407cb29d31c.png)


还有，每次回复ACK也是需要时间的，收到一条数据就返回一条ACK是很浪费资源的，现在我们等待一会，服务器回复一条ACK就可以了，从而减少了ACK的回复量。这也节约了资源。

延迟等待也不会等太久，一般有两个限制条件：
1. 数量限制：当客户端连续发送了两条数据过来，服务器必须回复一次ACK。
2. 时间限制：超过最大延迟时间必须回复（通常为200ms左右）。

总的来说这是一种提升效率的机制。

# 2. 捎带应答

这个就比较简单了。

举个例子。
我是一个很懒的人，晚上我躺在床上玩手机，现在我口渴了，但我不会去喝水。
我不想走那几步路。
过了一段时间，我现在想上厕所了，此时我就会在上厕所的同时去把水喝了。
原本两趟路此时我只用了一趟就完成了喝水与上厕所。

在三次握手那里也是同理，服务器返回的SYN与ACK都在同一个报头里。
再比如当服务器返回ACK的同时，如果有数据要给客户端的话，服务器就会把数据也塞进这个ACK报文里。而不是选择重新发送一个新的报文。

多发送一次就会增加丢包的风险，毕竟在互联网中，网络环境是非常复杂的。

# 3. 面向字节流

 我们知道TCP是以字节流的形式来进行数据的输入与传递的，
 UDP则是以数据报的形式来传递的。
 
先提一嘴UDP，这种方式更像是寄信。
假设你要给小美写情书，你肯定是要把告白的话写在这一个信里，
你不会把``我喜欢你``这四个字拆开分四封信寄。
小美打开信封就明白，这里面肯定是一段完整的话。

但TCP就不一样了。他传递信息的方式就如同水龙头中喷出的水一样，是连绵不绝的。TCP是将数据以字节为单位，传递给对方的，但这会造成一个问题，对方不知道如何断句，也就是说，不知道什么时候读取数据。

比如你先给别人发一句"hello",再给别人发"world",我们都知道是,"hello world ".
但由于面向字节流的原因，对方可能是这样断句的"he lloworld"....

这也是粘包问题。

# 4. 粘包问题

有三个方式可以解决粘包问题
1. 固定长度。
	通信双方定死一条数据有多长。
	比如：
	我们固定一个完整的传递所包含的数据长度是100。
	客户端发送102长度的数据，此时会被接收方截断为100+2，这100长度的数据从缓冲区中被读取走了，还剩下2长度的数据留在缓冲区。
	客户端发送75长度的数据，此时由于长度不够，剩下25长度。会用空白字符补齐剩下的25长度，从而凑够100长度，然后被服务器接收。	
2. 规定分割符号。例如在使用文本协议时，经常用换行符 `\n` 作为一条消息的结束标志。
	比如你输入 `"hello\nworld "` 那么接收方就会读取 hello，你要是输入 `"hellowo\nrd"`，那么接收方获得的数据就是 hellowo。
3. 头部加长度字段。
	这种方式就把一个TCP数据报分成了header部分与body部分。
	比如：
	在要传递的数据中，我们规定头部字段表示的是后续业务字段有多长，接收方就明白要读多少字节的数据。
	这种方式可以在HTTP的报头中看到，比如一个叫做 `Content-Length: 50` 的字段这里就表明了后续业务数据的长度。



# 5. 异常处理
最后我们看看假设两台主机之间的通信异常断开会触发什么结果：

1. 进程被杀死。
	当主机A进程因为某种原因突然暴毙后，此时的连接并未断开。此时内核会接管这条连接，并主动发起FIN。主机B会返回ACK。
	但是如果主机B还要传递剩下的数据时，由于主机A的进程描述符被操作系统释放了，接收缓冲区都释放了，所以数据也传不过来，这也代表进程死透了。主机B会收到主机A内核发送的 RST 报文，B收到RST后会主动删除进程的信息。
2. 拔电源
	这分为三种情况：

	主机B给主机A发送数据：
	此时主机B不会知道A已经暴毙了，他会如往常一样给主机A发送消息，但是得不到A返回的ACK，B会触发超时等待，当超过某个时限时，B会删除A的信息。

	主机B不给A发送消息，双方发呆：
	由于AB没有信息交互，会一直保持静默状态，B也不知道A死亡了。
	但如果双方保持没有信息交互的状态一定时间后，B会尝试给A发送一个无载荷的数据包，也就是所说的心跳包，来确认一下连接是否正常。

	主机A重启：
	此时A活过来了，但是内存中的数据早就被清空了，此时B给主机A发送信息时，A会不认识主机B，然后触发RST。
 
3. 拉网线
	仅仅拔掉网线这个物理动作本身，TCP 协议栈是完全无感知的！ TCP 是软件协议，它不知道硬件层面的网卡拔插事件，除非底层网卡驱动主动向上层报告，但很多系统里这个报告并不会直接中断 TCP 连接。

	双方都在发呆（没有数据交互）：
	如果你拔了网线，双方都不发数据。那么 A 和 B 都会以为对方还活着，双双保持 ESTABLISHED 状态。
	如果你在 1 个小时后把网线又悄悄插回去了，只要没触发 2 小时的 Keepalive 机制，A 和 B 的连接就依然是完好的！你发数据，照样能通！这就好像经历了一场漫长的网络延迟。

	主机 A（被拔网线的一方）尝试发数据：
	A 的应用程序发起了一次发送请求（如 write）。
	A 的内核把包发给了网卡，但网线没插，包出不去。
	A 会触发“超时重传机制”。A 的内核会不断尝试把包往外扔。如果在重传的那十多分钟里，你把网线插回去了，重传的包成功飞到了 B，那么这个连接就奇迹般地存活下来了，业务只觉得卡顿了一下，并不会报错。
	如果你死活不插回去，十多分钟后，A 的内核绝望，抛出超时异常。

	主机 B（没拔网线的一方）尝试发数据：
	这和“拔电源”的场景 1 完全一样。B 的包飞到了 A 所在的交换机，但找不到 A。B 只能不断重传，直到十多分钟后超时死心。

# 总结

1. 延迟应答：服务器等待片刻再回复ACK，以宣告更大的接收窗口，提高宏观传输效率并节约ACK开销。
2. 捎带应答：在发送ACK的同时顺带发送业务数据，减少网络报文数量，降低丢包风险。
3. 粘包问题：面向字节流的TCP无法像UDP那样区分数据边界，通常通过固定长度、规定分隔符或头部添加长度字段等三种方式解决。
4. 异常处理：TCP具备一定的容错与异常探测能力，面对进程崩溃内核能发送FIN或RST；面对物理断电或断网，将通过超时重传和心跳保活机制（Keepalive）来判断连接状态。
